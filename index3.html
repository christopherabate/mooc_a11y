Module 1 — Structure et organisation

Objectif : vérifier qu’un contenu possède une structure compréhensible, quel que soit le support utilisé.

Règles communes

  • Les titres suivent une hiérarchie logique.
  • Les listes utilisent une véritable structure de liste.
  • L’ordre de lecture est cohérent.
  • Les tableaux sont réservés aux données tabulaires.
  • La compréhension ne dépend pas uniquement de la mise en forme visuelle.

Web

Module 2 — Navigation et déplacement

Objectif : vérifier qu’une personne peut parcourir le contenu et atteindre tous les éléments utiles.

Règles communes

  • Tous les éléments interactifs sont atteignables.
  • L’ordre de navigation est logique.
  • Le focus est visible.
  • Aucun élément ne bloque la navigation.
  • Les actions ne dépendent pas uniquement de la souris ou d’un geste.

Comment tester selon le support ?

Web
  • Débrancher la souris.
  • Utiliser la touche Tab.
  • Vérifier que le focus est visible.
  • Tester Entrée, Espace, les flèches et Échap.
  • Vérifier l’absence de piège clavier.
Android et iOS
  • Activer TalkBack ou VoiceOver.
  • Balayer avec un doigt.
  • Vérifier l’ordre de lecture.
  • Tester toutes les actions proposées par les composants.
Documents
  • Tester le volet de navigation.
  • Lire le document avec un lecteur d’écran.
  • Vérifier l’ordre de lecture des blocs et des liens.
Maquettes
  • Définir le parcours clavier attendu.
  • Annoter l’ordre de lecture.
  • Documenter les changements d’écran.

Module 3 — Composants interactifs

Objectif : identifier correctement les liens, boutons, menus et autres contrôles.

Règles communes

  • Chaque composant possède un nom compréhensible.
  • Son rôle est identifiable.
  • Ses états sont perceptibles.
  • Son action est prévisible.
  • Les liens et les boutons sont distingués.

Activité — Lien ou bouton ?

Comment tester selon le support ?

Web
  • Vérifier les rôles HTML utilisés.
  • Utiliser a pour naviguer et button pour agir.
  • Vérifier le nom accessible.
  • Tester les états au clavier et à la souris.
Android et iOS
  • Vérifier que le type du composant est annoncé.
  • Vérifier les états activé, désactivé, sélectionné et ouvert.
  • Vérifier les actions disponibles.
Documents
  • Tester les liens et les champs de formulaire.
  • Vérifier que les éléments décoratifs ne sont pas interactifs.
Maquettes
  • Documenter le nom, le rôle et le comportement.
  • Prévoir les états repos, focus, actif, erreur, succès et chargement.

Module 4 — Formulaires et erreurs

Objectif : vérifier qu’un formulaire peut être compris, complété et corrigé.

Règles communes

  • Chaque champ possède une étiquette visible.
  • Le placeholder ne remplace pas l’étiquette.
  • Les champs obligatoires sont clairement indiqués.
  • Les messages d’erreur indiquent le champ concerné et le problème.
  • Le message d’erreur est associé au champ.

Comment tester selon le support ?

Web
  • Vérifier l’association entre label et input.
  • Indiquer les champs obligatoires en toutes lettres ou expliquer l’astérisque.
  • Associer l’erreur avec aria-describedby.
  • Tester l’annonce avec un lecteur d’écran.
Android et iOS
  • Vérifier le nom, le type et l’état obligatoire du champ.
  • Saisir une valeur incorrecte.
  • Vérifier l’annonce de l’erreur.
  • Vérifier que le clavier ne masque pas le message.
Documents
  • Tester les champs avec un lecteur d’écran.
  • Vérifier les noms et instructions des champs.
  • Vérifier les indications obligatoires.
Maquettes
  • Prévoir les états vide, rempli, obligatoire et erreur.
  • Prévoir les états validation, succès et chargement.

Module 5 — Lisibilité, agrandissement et adaptation

Objectif : vérifier que le contenu reste utilisable lorsque la taille du texte ou de l’écran change.

Règles communes

  • Le contenu reste lisible avec un texte agrandi.
  • Les informations ne sont pas coupées.
  • Les composants ne se chevauchent pas.
  • La mise en page s’adapte aux petits écrans.
  • Les unités relatives sont privilégiées.

Comment tester selon le support ?

Web
  • Agrandir l’affichage à 200 %.
  • Tester une largeur équivalente à environ 320 pixels CSS.
  • Vérifier l’absence de défilement horizontal inutile.
  • Vérifier que les contrôles restent utilisables.
Android et iOS
  • Augmenter la taille du texte dans les réglages.
  • Tester les tailles de texte importantes.
  • Tester les orientations prévues.
  • Vérifier que les contenus ne sont pas coupés.
Documents
  • Agrandir le texte.
  • Vérifier l’ordre de lecture.
  • Tester le document exporté en PDF.
Maquettes
  • Tester les largeurs réduites.
  • Tester les textes longs et les traductions.
  • Tester une taille de caractères importante.

Module 6 — Contrastes et utilisation de la couleur

Objectif : vérifier que les textes, composants, graphiques et états restent perceptibles.

Règles communes

  • Le texte normal atteint généralement un contraste de 4,5:1.
  • Les grands textes atteignent généralement un contraste de 3:1.
  • Les composants essentiels et le focus atteignent généralement 3:1.
  • La couleur ne constitue jamais la seule information.

Activité — Quel texte est le plus lisible ?

Choisissez la combinaison la plus contrastée.

Comment tester selon le support ?

Web
  • Utiliser Colour Contrast Analyser, axe DevTools ou Lighthouse.
  • Tester les textes, bordures, états et indicateurs de focus.
  • Vérifier que les erreurs ne reposent pas uniquement sur la couleur.
Android et iOS
  • Tester les états sélectionné, désactivé, erreur et focus.
  • Activer les réglages de contraste renforcé.
  • Vérifier que les informations sont aussi transmises par le texte ou une forme.
Documents
  • Utiliser un vérificateur de contraste.
  • Tester le document en niveaux de gris.
  • Contrôler les graphiques et illustrations informatives.
Maquettes
  • Tester les couleurs avec un outil de contraste.
  • Tester tous les états des composants.
  • Prévoir une information complémentaire à la couleur.

Module 7 — Images et alternatives textuelles

Objectif : déterminer si une image est décorative, informative, fonctionnelle ou porteuse d’une information complexe.

Règles communes

  • Une image décorative peut être ignorée.
  • Une image informative possède une alternative pertinente.
  • Une image fonctionnelle décrit l’action déclenchée.
  • Les informations importantes ne sont pas uniquement présentes dans une image.
  • Les graphiques complexes possèdent une description adaptée.

Module 8 — Langue, titres et contexte

Objectif : vérifier qu’une personne comprend où elle se trouve et dans quelle langue le contenu doit être interprété.

Règles communes

  • Chaque page ou écran possède un titre explicite.
  • La langue principale est définie.
  • Les changements de langue sont signalés.
  • Les liens et boutons sont compréhensibles hors contexte.
  • Les libellés répétés sont suffisamment contextualisés.

Règles communes

  • Les contrôles sont suffisamment espacés.
  • Les gestes complexes possèdent une alternative.
  • Les actions ne dépendent pas uniquement du mouvement.
  • Les commandes restent utilisables dans l’orientation prévue.

Module 10 — Audio, vidéo et animations

Objectif : vérifier que les contenus multimédias peuvent être compris et contrôlés.

Règles communes

  • Les vidéos possèdent des sous-titres lorsque cela est nécessaire.
  • Une transcription est disponible.
  • Une audiodescription est prévue lorsque les informations visuelles sont indispensables.
  • Les contrôles sont accessibles.
  • Les animations automatiques peuvent être mises en pause ou arrêtées.

Module 11 — Messages, changements d’état et robustesse

Objectif : vérifier qu’une personne est informée des changements importants sans devoir les deviner.

Règles communes

  • Les états de chargement sont perceptibles.
  • Les réussites et les erreurs sont annoncées.
  • Les changements d’état sont compréhensibles.
  • Les actions irréversibles sont confirmées.
  • Les messages ne reposent pas uniquement sur la couleur, le son ou une animation.
